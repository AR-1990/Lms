# Pinnacle School ERP — Master Plan & Database Design

This file is the single source of truth for what the system contains and how the database is shaped.
Read it before adding a table or field, and update it in the same change when the schema changes.
Project rules (API-first, no JSON storage, dynamic options, Yajra DataTables, etc.) are in `AGENTS.md`.

**One API, every screen.** Every module is built once as an API and the same endpoints serve the web admin panel, all web portals, and the Android/iOS mobile apps. No feature is built twice. See section 24.

**Modules**

0. Core & shared (users, campuses, lookups, attachments, activity log)
1. Academic foundation (sessions, classes, sections, subjects, timetable, calendar)
2. Admissions (inquiry → application → documents → test → interview → offer → enrolment)
3. Student management (profiles, guardians, enrolment history, status changes, discipline, medical)
4. Student attendance & leave
5. Exams management (date sheets, halls, seating, admit cards, marks, results), homework & daily diary
6. Fee management (incl. admission fee structure and exam fees)
7. Payments & payment methods
8. Accounts & general ledger (double-entry)
9. Recruitment (job opening → application → interview → offer → hiring)
10. Employee management
11. HR (staff attendance, leave, payroll, loans, appraisals, exit)
12. Asset management (fixed assets and who holds them)
13. Inventory & procurement (consumable stock and who was issued what)
14. Communication (announcements for students / parents / employees / public, real-time employee chat like WhatsApp, SMS/email/push logs)
15. Transport (optional)
16. Portals (teacher, student, parent, accounts) — screens built on top of the other modules
17. Student performance tracker (trends, skills, goals, at-risk alerts)
18. Task management (boards, assignees, checklists, reminders)
19. Sticky notes (personal reminder notes shown on every user's dashboard)

Plus: Printables & cards (section 23) and the one API for web + mobile (section 24).

## 1. Global conventions

| Convention | Rule |
|---|---|
| Primary key | `id` bigint auto-increment on every table |
| Timestamps | `created_at`, `updated_at` on every table |
| Soft deletes **[SD]** | `deleted_at` on **every** table whose rows can be deleted (people, masters, settings rows, child/line rows, pivots). Nothing is ever permanently deleted; only Sanctum tokens / sessions / cache are hard deleted. Tables built before this rule that still lack `deleted_at` are converted in one migration (see section 26) |
| Audit columns **[AU]** | `created_by`, `updated_by` → `users.id`, nullable |
| Relations (no FK constraints) | Every `→ table` column is a plain `unsignedBigInteger` with an **index**, never a database foreign-key constraint, so data can be exported, imported, and moved between databases/campuses freely. Integrity is enforced in the application: `exists:` validation, soft deletes instead of hard deletes, and Services that refuse to delete a record still in use |
| Activity log | Every create / update / delete / status change / approve / post / print / export / login is written to `activity_logs` (+ field changes in `activity_log_changes`) in the same transaction. One screen shows who did what, on which module, when |
| Campus **[C]** | `campus_id` → `campuses.id`, nullable — ready for multi-campus without a redesign |
| Money | `bigInteger`, stored in minor units (paisa): Rs 1,500.50 = `150050`. Never float/decimal |
| Quantities | `decimal(12,3)` for stock quantities (allows 0.5 kg etc.) |
| Booleans | `boolean` with a default |
| Statuses | `string(30)` holding a fixed workflow code (e.g. `draft`, `posted`). Business options use lookups instead |
| Options / categories | `lookup_id` → `lookups.id`, or a dedicated master table. Never PHP enums or JSON |
| Files | Stored on a `Storage` disk; metadata in `attachments`. Profile photos may use `photo_path` |
| JSON | Never stored. JSON is only the API response format |
| Optional fields | Everything not marked **required** is nullable |
| Indexes | Every reference (`_id`) column, plus every column used to filter, search, or sort |
| Codes / numbers | Human codes (admission no, employee code, invoice no) are `string`, unique, generated by the system using a per-type counter in `number_sequences` |

Notation in the tables below: **R** = required, everything else is optional (nullable). `→ table` means an indexed reference column to that table (no database FK constraint).

## 2. Key business flows

### 2.1 Student: inquiry to enrolment
```
Inquiry (call / walk-in / website form)
  → Application (form + registration fee)
    → Document verification (B-Form, previous result, photos)
      → Entry test (scheduled, marks recorded)
        → Interview (student + parents, panel feedback)
          → Decision: offered / waitlisted / rejected
            → Offer accepted + admission fee invoice paid
              → Enrolled: student + guardians + enrolment + portal accounts created automatically
```
Every step change is written to `admission_status_histories` (who, when, remarks).

### 2.2 Employee: job opening to hiring
```
Job opening (department, designation, positions, closing date)
  → Applications received (website / walk-in / referral, CV upload)
    → Shortlisting
      → Interview rounds (one or many, panel scores + feedback)
        → (optional) Demo lecture / test for teaching posts
          → Offer letter (salary, joining date) → accepted / declined
            → Hired: employee record + contract + salary structure + portal account created
```
Every step change is written to `job_application_status_histories`.

### 2.3 Money flow (every money event posts to the ledger automatically)
| Event | Debit | Credit |
|---|---|---|
| Fee invoice posted | Student Receivable | Fee income account of each fee head |
| Concession on invoice | Concession / Discount Expense | Student Receivable |
| Late fine added | Student Receivable | Late Fine Income |
| Fee payment received | Cash / Bank (per payment method) | Student Receivable |
| Fee refund | Security Deposit (the refundable head's account, 2500) or Student Advances (2300) | Cash / Bank (per payment method) |
| Payroll posted | Salary Expense (per component) | Salaries Payable + Tax/EOBI/PF Payable |
| Salary paid | Salaries Payable | Bank |
| Loan given to employee | Employee Loans Receivable | Cash / Bank |
| Loan instalment deducted | Salaries Payable | Employee Loans Receivable |
| Expense paid | Expense account | Cash / Bank |
| Purchase received on credit | Inventory / Fixed Asset | Accounts Payable (vendor) |
| Vendor paid | Accounts Payable | Cash / Bank |
| Asset depreciation | Depreciation Expense | Accumulated Depreciation |

Which ledger account each event uses is configured, not hard-coded: fee heads, payment methods, salary components, expense categories, and asset/item categories each carry their own `account_id`.

### Admission fee structure
Admission charges are rows of the same class fee structure, so every class and session can have its own admission package without new tables:

| Stage | `charge_on` | Typical fee heads | When the invoice is created |
|---|---|---|---|
| Registration | `on_application` | Registration / Prospectus Fee, Entry Test Fee | When the admission application is submitted |
| Admission | `on_admission` | Admission Fee, Security Deposit (refundable), Annual Charges, first month Tuition, Books & Uniform package (optional) | When the offer is accepted; paying it completes enrolment |

## 24. One API for web + mobile (build once, use everywhere)

Every feature is built **once** as an API. The same endpoints are used by the web admin panel, the web portals (teacher, student, parent, accounts), and the Android and iOS apps. Nothing is built separately for mobile.

**Base & structure**
- All endpoints live under `/api/erp/...` (current convention), grouped by module, behind `auth:sanctum` and `permission:` middleware.
- Controller → Service → Model; Blade screens and mobile apps call the same Services through the same routes.
- Output is shaped with Eloquent API Resources so web and mobile receive identical fields.

**Authentication**
- Mobile: `POST /api/login` returns a Sanctum personal access token (one per device) plus the user, roles, permissions, and available portals.
- Web: the same endpoints, authenticated with the Sanctum session (stateful SPA / Blade).
- Logout revokes only that device's token; "log out of all devices" revokes all.
- Caching (any `CACHE_STORE`; database now, Redis later is a `.env` change): each user's role and permission slugs (`User::access`, cleared on any role, permission or assignment change through a version key), the runtime timezone / school name (`SystemSettingsService`), dropdown lists per type (`LookupService::options`, cleared by `Lookup` model events), public website pages and school details (`WebsitePageService`, cleared when a page, block, card or the settings change), the admin money dashboard (60 s) and on-screen reports (120 s; CSV / PDF always fresh). Running migrations clears the whole cache; bulk query-builder updates skip model events, so data that is cached must be changed through its model or Service. Role and permission links go through the `RoleUser` / `PermissionRole` pivot models, so any attach / detach / sync clears access automatically. Only the classes listed in `config/cache.php` → `serializable_classes` can be read back from the cache (Laravel blocks all others by default); cache plain arrays where possible, and add a class there before caching a new model. Tests run the array cache with serialization on (`CACHE_ARRAY_SERIALIZE`), so a value that cannot be restored fails in tests as it would on the database / Redis store.
- No public sign-up: accounts are created by the school (admissions, HR, Users). `/api/register` does not exist.
- Sign-in is rate-limited (`throttle:login`): 5 tries a minute per account + IP and 20 a minute per IP, on both `POST /login` (error shown on the form) and `POST /api/login` (429 in the standard envelope). Password reset requests use `throttle:password-reset` with the same limits.
- Mobile tokens have no fixed expiry; a token unused for `SANCTUM_IDLE_DAYS` (default 60) stops working and is pruned nightly at 03:00 with its `user_devices` row set inactive. Tokens of a disabled account are refused.
- Disabling an account, deleting it or resetting its password deletes its tokens and its database sessions; the `EnsureAccountIsActive` middleware (web and api groups) also ends a disabled account's session on its next request, whatever the session driver.
- Forgot password: `GET /forgot-password` and `GET /reset-password/{token}` (Blade) post to `POST /api/forgot-password` (`identifier` = ID, email or phone; always the same answer, so it never reveals which accounts exist) and `POST /api/reset-password` (`token`, `email`, `password`, `password_confirmation`). The link is emailed (Laravel password broker, `password_reset_tokens`, 60-minute links); accounts without an email must ask the school office. The mobile apps use the same two endpoints.

**Response format** (rule 3 in `AGENTS.md`): always `{ success, message, data, errors }`.
- Single record: `data` = the resource.

Public website content for apps: `GET /api/site` (school details, shared blocks, home), `/api/site/news`, `/api/site/contact`, `/api/site/pages/{slug}` — shaped once in `PublicSiteService` for both the website and the API. Device push tokens are stored (`PUT /api/erp/devices/push-token`); every in-app notification is also pushed to the user's phones through Firebase once `FIREBASE_PROJECT_ID` and `FIREBASE_CREDENTIALS` (service-account key file) are set (queued, logged in `notification_logs` with channel `push`; a token Firebase reports as unregistered is cleared).
- **Family portal** — Parents (Child Overview) and students (My School Day) open `/family/students/{id}`: header with class, roll no, class teacher and bus; tiles for this month's attendance, fees due, next paper and latest result; tabs Today (today's periods, the last two weeks of diary / homework with "Sign" for parents, the weekly timetable), Attendance (any month, day by day), Exams & Results (date sheets, admit card and report card PDFs, subject marks), Fees (unpaid challans and every receipt as PDF), Leave (parents ask for leave; status of recent requests) and Year by year (with the School Leaving Certificate once issued). One call `GET /api/erp/family/students/{id}` (and `GET /api/erp/family/students` for the child switcher) feeds the page and the mobile app; families see only their own children. Exports: `fees/payments/{id}/pdf` (A5 receipt, staff or the child's family), `exams/{exam}/admit-cards/students/{student}/pdf` (eligible only) and `exams/{exam}/report-cards/students/{student}/pdf` (published only); `students/{id}/history` and the leaving certificate PDF are also open to the child's family. Students now have `view-fees`.
- **Family notifications** — In-app (and SMS where a template exists, logged until a provider is chosen) through the message templates: `challan_issued` (each challan with something to pay), `payment_received`, `fee_overdue` (the morning after the due date, once), `diary_published` (first publish of a section's diary, with the entry types), `leave_decided`, `admit_card_ready` (when a card becomes eligible), plus the existing `absent_alert` and `result_published`. Each opens the child's page.
- **School logo** — stored as a file (`system_settings.logo_path`, local disk `branding/`), served at `/school-logo` and printed on challans, receipts and certificates.
- **Enrolment** — enrolling an accepted applicant can also make this month's fee challan, issue the ID card (when a student card template exists) and create the student login (signs in with the admission number); "Create login" on the profile does the same later (`POST /api/erp/students/{id}/portal-account`).
- **Hosting** — no Redis needed: cache, sessions and queue use the database; the single cron entry `* * * * * php artisan schedule:run` also works through the queue every minute (`queue:drain`).
- **Data import** — Admin → Data Import (`manage-settings`; each type also needs its module permission): CSV templates (`imports/{type}/template`) for students, staff, opening fee balances and staff attendance punches. Rows are checked with the same rules as the forms (dry run first), and saved all-or-nothing (max 2,000 rows). A positive opening balance becomes an OPB challan (fee head `OPB`, account 3300); a negative one is received as advance through the inactive system method `OPENING`.
- **Multi-campus** — Campus-owned records (students, staff, admissions, fees, expenses, assets, ID cards, exams, classes, departments, locations, fee structures, card templates, halls, periods, job openings, purchases, approvals, calendar) carry `campus_id`. A user with a campus sees that campus plus shared rows (campus empty); head-office users (no campus, or `manage-campuses`) see everything and can pick a campus in the top bar (sent as `X-Campus-Id`). New rows take the user's (or picked) campus.
- **Backups** — Nightly at 02:30 (`backup:run`) a gzip SQL dump of the whole database goes to `storage/app/private/backups` (last 14 kept); Settings → Backups lists them, makes one now and downloads (`manage-settings`; `GET/POST /api/erp/admin/backups`, download `admin/backups/{file}`).
- **Approvals inbox** — One page (`/approvals-inbox`, `GET /api/erp/approvals/inbox`) lists everything waiting for the signed-in user's decision — delete requests, expenses, purchase orders, loans, concessions, staff and student leave — each with Approve / Reject calling that module's own endpoint.
- **ID cards** — New look "Modern angled header" (`theme` `modern`, the default student and staff templates on a fresh install) and a card item `school_logo` (the school logo from Settings) for every card type; the QR on the card is the gate-attendance code.
- **Jump to** — The top bar search (Ctrl K or "/") lists every page the user may open, grouped by module (`GET /api/erp/jump-to`), read from the named web routes and their permissions, so new screens appear by themselves.
- **Automatic absent & arrival alerts** — `system_settings.auto_absent_at` (Attendance → Live Today, `GET/PUT /api/erp/attendance/settings`, `manage-students`; empty = off): for gate-scanning schools, after that time every student of the current session with no mark is made absent (`source` `auto`; approved leave becomes "leave") and families get the absent alert; Sundays and holidays are skipped. A student who scans in later becomes "late". Every gate / QR check-in sends the family the `student_arrived` message ("arrived at school 7:52 AM").
- **Fee reminders before the due date** — `system_settings.fee_reminder_days` (Fees → Late Fees & Automation): each morning (09:15) families of challans due within that many days get the `fee_due_soon` message, once per challan (`fee_invoices.reminder_sent_at`).
- **SMS / WhatsApp** — sent through the school's provider HTTP API once `SMS_GATEWAY_URL` / `WHATSAPP_GATEWAY_URL` are set (`{to}` `{message}` `{sender}` placeholders, GET or POST form fields, optional Bearer token); numbers become 92XXXXXXXXXX. Queued and logged like email.
- **Online test questions from CSV** — the test builder can copy questions from an earlier test or read a CSV (`question, marks, correct (A–F), option_a … option_f`; template `imports/online_test_questions/template`), checked by the data importer and added to the builder before saving.
- **Morning summary** — Monday to Saturday at 10:30 everyone with `view-stats` (and administrators) gets one notification: students present so far, staff in, yesterday's collection, overdue fees, new enquiries and what waits for approval.
- **Overdue fee alerts** — Every morning at 09:00 (`fees:overdue-alerts`) everyone who manages fees (administrators and the accounts role) gets one in-app notification: how many students have challans unpaid after the due date and the amount, naming up to five who became overdue yesterday (marked urgent when there are new ones). It opens Fees → Challans with the new **Overdue (past due date)** filter (`status=overdue`).
- **Fee flow notes** — Late fines are applied nightly at 00:30 (`fees:late-fines`): for each active rule, every unpaid challan of its type whose due date + grace days has passed gets what the rule asks for and has not yet added (fixed or percent once, per-day growing to `max_amount`); paid or cancelled challans are never fined. Monthly challans can generate themselves on `system_settings.fee_auto_generate_day` (1–28, or 31 = last day of the month; null = off) at 06:00 (`fees:auto-challans`), once per month for all classes of the current session; fee staff are notified of both. A new challan for a student with unused advance is paid from it at once; cancelling a challan paid only from advance returns the advance, and reversing a receipt also takes back any advance it had already applied. Challan PDF: three copies (bank / school / student) per A4 landscape page with the default fees bank account, fines and the late-fine notice — `GET /api/erp/fees/invoices/{id}/pdf` (staff, or the child's own parent / student) and `/api/erp/fees/batches/{id}/pdf` (a monthly batch, up to 500). Screens: Fees → Late Fees & Automation; Print on the challan popup; "open the challans to print" when generating; Download challan on the parent Fees page. A starter rule (Rs 500 after 5 days, monthly) is seeded switched off.
- **Phase 17e notes** — Reports are computed from the module tables; no new tables. The catalogue and each report follow the module permission (finance `view-ledger`; fees `view-fees` / `manage-fees`; students `manage-students`, admissions also `manage-admissions`, attendance also `record-attendance`; HR `manage-hr`, staff attendance `manage-staff-attendance`, leave `manage-leave`, payroll `manage-payroll` / `view-payroll`; `manage-expenses`, `manage-inventory`, `manage-assets`, `manage-transport`). API `GET /api/erp/reports` and `/api/erp/reports/{key}` (long lists paginated, 50 a page); CSV and PDF in routes/export.php (`/api/erp/reports/{key}/csv|pdf`), CSV streamed in chunks, PDF capped at 1,000 rows; every export and print is activity-logged. The Balance Sheet adds the surplus to date under equity, so it balances without a year-end closing entry.
- **Phase 17d notes** — Added beyond §20: `counselling_notes.performance_alert_id`, `action_plan`, `follow_up_done_at` and [SD]. Permission `manage-counselling` (admin); the screen is Performance → Counselling. Saving a session with an open alert of the same student sets the alert to `acknowledged` with "Counselling session on <date>" as the action. Changing the follow-up date clears `follow_up_done_at`. Scheduler `counselling:follow-up-reminders` daily at 07:30 (notification `counselling_follow_up`). No demo sessions are seeded (sensitive data); `counselling_concern` lookups are seeded.
- **Phase 17c notes** — Added beyond §14.5: `appraisal_cycles.department_id`, `self_review`, `launched_at`, `closed_at`; `appraisal_criteria.description`, `applies_to`, `sort_order`; `appraisals.self_score`, `goals`, `self_reviewed_at`, `submitted_at`, `acknowledged_at` and status `self_review`; `appraisal_scores.self_score`, `self_comment` (`score` is nullable until the reviewer scores). All four tables [SD], the first three [AU]. Scores are 1–5; the overall is the weight-weighted mean (plain mean when no weights). The suggested rating splits 1–5 into equal bands over the active `appraisal_rating` lookups in sort order (first = best). The employee sees reviewer scores only after submission. Permission `manage-appraisals` (admin); reviewers and employees need no permission — access is by being the reviewer or the person appraised. Criteria and this year's cycle (draft) are seeded.
- **Phase 17b notes** — Added beyond §18: `vehicles.make_model`, `vehicles.route_permit_expiry`, `vehicles.is_active`; `transport_routes.attendant_employee_id`; `student_transport.transport_route_id` (copied from the stop for fast lookups) and `remarks`; all four tables [SD] [AU]. Ride status `active` / `ended`. The fee head defaults to `TRN` (Transport Fee); the challan line is the stop's `fee_override` or the route `monthly_fee`, charged for every month a ride overlaps. Lookup list `transport_stop_area` seeded; permission `manage-transport` (admin); scheduler `transport:expiry-alerts` daily at 08:00. Demo routes and vehicles are seeded without riders so demo fee challans stay unchanged.
- **Sign-in** — one form for everyone (ID/email + password); the account's roles choose the portal. The sign-in page text is the `login` website page (Website → Pages).
- **Diary remark types** carry a code (`positive` / `negative` / `neutral`) that the performance tracker counts.
